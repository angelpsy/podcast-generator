## Результат

Прототип выполнил экспериментальную задачу: вход, разрешение подписки, ответ, выход и повторный вход подтверждены в [отчёте устройства](DEVICE_TEST_2026-10-25.md). Для этой цели архитектура соразмерна: один RN-экран, один Kotlin coordinator, отдельные протокол и защищённое хранилище. Дополнительные слои, DI-фреймворк, навигация и backend сейчас не требуются.

Найдено **два замечания P2** в восстановлении сессии. Их стоит закрыть перед длительным использованием и проверкой истечения токенов. Они не опровергают уже полученный результат эксперимента. P0/P1 в проверенном объёме не обнаружены. Это ревью, а не полный аудит безопасности.

Код приложения в рамках ревью не изменялся. Замечания ниже остаются открытыми; сценарии установлены анализом кода и контракта, но не воспроизводились на реальном аккаунте. Исправленные ранее сбои описаны отдельно в [журнале ошибок](SIWC_ERROR_LOG.md).

## R-01 · P2 · Не все терминальные ошибки refresh завершают недействительную сессию

**Место:** [SiwcCoordinator.kt](../mobile/android/app/src/main/java/dev/podcast/siwcspike/siwc/SiwcCoordinator.kt), строки 175–177 и 335–337 указанной версии.

**Условие:** token endpoint возвращает `token_expired`, `refresh_token_expired` или `refresh_token_invalidated`. Официальный контракт относит эти коды к непригодному refresh-токену. [OpenAI: Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

**Поведение:** `safeHttpError` превращает эти коды в общий `http_400`/`http_401`, поскольку они отсутствуют в allowlist. `refresh()` очищает токены только для трёх других кодов. В результате `signedIn` и `planEnabled` остаются истинными, кнопки запросов доступны, а следующая попытка снова использует непригодный refresh-токен. Вместо понятного предложения войти заново пользователь получает повторяющуюся HTTP-ошибку. Ручной Continue with ChatGPT остаётся обходным путём.

**Предлагаемое исправление:** использовать единый набор терминальных кодов для безопасного разбора и очистки токенов; сохранять client ID/host ID и показывать предложение повторного входа. Сетевые сбои, 5xx и ошибки конфигурации клиента не должны очищать сессию.

**Проверка исправления:** подставить каждый документированный терминальный код в ответ refresh; убедиться, что локальные токены очищены, запросы отключены, mapping сохранён и следующий вход использует прежний client ID. Отдельно проверить сохранение токенов при IOException/5xx. Сейчас таких coordinator-тестов нет.

## R-02 · P2 · Новый refresh-токен теряется при сбое проверки JWKS после ротации

**Место:** [SiwcCoordinator.kt](../mobile/android/app/src/main/java/dev/podcast/siwcspike/siwc/SiwcCoordinator.kt), строки 329–333; сетевой запрос в `validate()` — строка 217.

**Условие:** refresh уже ответил HTTP 200 с новым refresh-токеном и ID-токеном, затем загрузка JWKS падает из-за сети либо пользователь отменяет операцию до неё. Успешный refresh выдаёт замену токена; использовать и сохранять нужно последнюю замену. [OpenAI: Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

**Поведение:** `validate()` каждый раз выполняет отдельный HTTP-запрос. Исключение прерывает выполнение до `saveTokens()`. Полученный ответ существует только в локальной переменной и теряется; в хранилище остаётся предыдущий refresh-токен. Следующая попытка повторяет его, хотя сервер уже выполнил ротацию. Это может привести к `refresh_token_reused`/`invalid_grant` и лишнему повторному входу после временного сетевого сбоя или отмены. Конкретный ответ сервера при повторном использовании на Pixel не проверялся.

**Предлагаемое исправление:** получать/кэшировать JWKS до ротации, отдельно обрабатывать стадию «новый ответ получен, проверка ещё не завершена» и повторять проверку этого ответа, а не refresh старым токеном. Непроверенные credentials не делать активными. Для восстановления после убийства процесса потребуется защищённая промежуточная запись; её можно оставить за границами v0, явно сохранив ограничение. Отмену после успешной ротации нужно согласовать с завершением безопасного сохранения сессии.

**Проверка исправления:** изолированный сценарий `refresh(r1) → 200(r2, id_token) → JWKS IOException`, затем восстановление сети. Проверить отсутствие второго запроса с `r1` и активацию `r2` только после проверки подписи/identity. Повторить с отменой между ответом token endpoint и JWKS. Неверная подпись или другая identity должны по-прежнему отклоняться.

## Что соответствует задаче v0

- Случайные state/nonce/verifier, PKCE S256, точный loopback callback и проверка ID-токена через Nimbus; разрешение подписки проверяется отдельно.
- Повторный вход использует сохранённую регистрацию и проверяет прежний `sub`; выход сохраняет mapping и удаляет access/refresh/ID tokens.
- Токены остаются в Kotlin и шифруются через Android Keystore; JS и экспорт диагностики их не получают. Backup отключён.
- Операции сериализованы одним executor. Состояние принадлежит процессу; UI подписывается на snapshots и отсеивает устаревшие revisions.
- SSE без Content-Type допускается только по ожидаемому началу потока. `[DONE]` и EOF не заменяют `response.completed`.
- `AwaitingReturn` устранил наблюдавшийся сбой обмена кода в фоне без изменения TLS/DNS или настроек телефона.

## Допустимые ограничения первой версии

Один аккаунт, ручной возврат из браузера, потеря незавершённого входа при убийстве процесса, arm64 и тестовая подпись APK соответствуют эксперименту. Отсутствие TTS, фоновой генерации, базы подкастов, CI, Play-публикации и сложной UI-архитектуры не считается дефектом этой версии.

Неблокирующие улучшения при дальнейшем развитии: хранить статус ответа отдельно от общего этапа (сейчас загрузка моделей после Completed меняет подпись под прежним ответом); добавить идентификатор сборки в диагностику; вынести HTTP/credential зависимости coordinator для проверок с подставными ответами. Ограничения размера в `safeHttpError` и SSE применяются после чтения целого тела/строки — до работы с длинными потоками стоит ограничить само чтение. Автоматический retry revocation с backoff пока отсутствует; локальный выход с предупреждением уже предусмотрен.
