# Этап 3: топики и ручная структура

Дата: 25 октября 2026, Asia/Tbilisi. Android **1.5 / versionCode 6**, Pixel 10 Pro / Android 17. Application ID и ключ подписи сохранены. Обновление поверх 1.4 выполнено через `adb install -r`, без очистки данных. **Этап 3 завершён**; ниже зафиксированы выполненные проверки и границы.

## Реализовано

В приложении три вкладки: «Подкасты», «Топики», «Настройки». Для топиков используются React Navigation native-stack и bottom-tabs ранее проверенных версий; MainActivity устанавливает RNScreensFragmentFactory перед super.onCreate. Мини-плеер общий для вкладок. Генератор подкастов не размонтируется при переключении вкладки.

Пользователь может создать топик с названием и целью, редактировать его, добавить раздел или конечный вопрос, изменить название/описание/тип узла, удалить ветку и целый топик. Перенос — выбор родителя внутри текущего топика; порядок соседей — «Выше/Ниже». Кнопки и выбор родителя используют ту же native-валидацию, что и команды. Android Back возвращает к родителю ветки, затем к списку топиков; есть breadcrumbs.

Прикрепление готового выпуска выполняется поиском по названию, по 50 записей на страницу. Регистр/ё и литеральные `%`/`_` обрабатываются по прежним правилам библиотеки. В выборе видны длительность и дата добавления: выпуски с одинаковым названием различимы. Один подкаст можно связать с несколькими узлами и топиками; аудиофайл не копируется.

Первый выпуск при отсутствии основного становится MAIN, остальные — EXTRA. Можно назначить другой основным: прежний остаётся дополнительным. Дополнительные упорядочиваются «Раньше/Позже». Отвязка удаляет только связь; удаление ветки/топика удаляет только структуру и её связи. Все разрушительные действия UI требуют подтверждения с описанием последствий.

В каждой ветке доступны режимы «Структура / Слушать». Плейлист вычисляется: MAIN узла, EXTRA по порядку, затем дочерние ветки в глубину. Один podcast ID включается единожды; недоступные записи видны, но не входят в новую очередь. «Слушать ветку» передаёт в существующий MediaController снимок IDs. Перенос, переименование, отвязка и удаление топика не меняют уже запущенную очередь. Единичный выпуск также можно запустить из узла.

Это ручной этап: **запросы структуры к OpenAI и создание новых подкастов из узлов не реализованы и не запускаются**. Существующий одиночный генератор остаётся на вкладке подкастов. Языковой профиль связей пока ru_standard.

## Хранение и инварианты

Room **3**, новая явная миграция **2 → 3**, зарегистрирована цепочка **1 → 2 → 3**. Предыдущие схемы оставлены; экспортирована `mobile/android/app/schemas/dev.podcast.siwcspike.podcast.PodcastDatabase/3.json`. Destructive fallback отсутствует.

| Таблица | Данные / ограничения |
| --- | --- |
| `topics` | UUID, rootNodeId, название, цель, outlineDepth, revision, createdAt/updatedAt |
| `topic_nodes` | UUID, topicId, parentId, ROOT/SECTION/QUESTION, название/описание, position, revision, rootSlot |
| `node_podcasts` | Уникальная пара node/podcast, MAIN/EXTRA, profile, position, mainSlot |

FK parent `(parentId, topicId)` → `(id, topicId)` исключает чужого родителя на уровне SQLite. Индексы уникальности rootSlot и mainSlot защищают единственный корневой/основной слот; repository обеспечивает согласованность kind/role со слотами. FK удаляют дочерние узлы и связи, а не родительские подкасты. Правила дерева дополнительно проверяются транзакционным repository; прямое произвольное SQL-редактирование не является публичным API.

- Корень на уровне 0; до **4 уровней ниже корня**. Перенос учитывает высоту всей ветки, а не только перемещаемого узла.
- До **200 узлов вместе с корнем**. QUESTION не имеет детей. Корень нельзя переместить или удалить отдельно.
- Перенос только в текущем топике; в себя/потомка запрещён. После удаления/переноса позиции соседей нормализуются в той же транзакции.
- Названия 1–200 Unicode code points, описания/цель до 2000. ID узла не меняется при переносе/редактировании.
- До 50 связей на узел и 1000 готовых IDs в запускаемой очереди.
- Snapshot и мутации — Room transactions. Каждая мутация существующего топика проверяет expectedRevision; конфликт не применяет старые изменения. UI сохраняет форму с ошибкой и предлагает закрыть/обновить данные, не подменяет версию молча.
- При явном удалении выпуска из библиотеки зависимые топики получают новую revision в транзакции удаления записи; FK затем удаляет связи. Обычная отвязка и удаление топика аудиофайлы не затрагивают.

Topic.outlineDepth хранится для будущих предложений структуры; в ручной форме пока не редактируется. Его уменьшение через API не обрезает дерево. Все bearer/refresh-токены остаются в прежнем SIWC-хранилище. Данные каталога не дублируются в AsyncStorage/JS SQLite.

Ручной цикл: «Топики» → создать → добавить разделы/вопрос → изменить/перенести/порядок → прикрепить из поиска → «Слушать» → «Слушать ветку» → изменить структуру → проверить неизменность активной очереди → перезапустить → проверить данные → удалить только собственный проверочный топик. ## Границы

AI-план — этап 4; генерация выпусков по узлам, языковые/контентные профили и пакетная очередь — этап 5. Ручные плейлисты, теги, оформление и удаление прежних SIWC/голосовых диагностических элементов ещё не выполнены. Перенос между топиками и drag-and-drop не реализованы; кнопки обеспечивают доступный порядок/перенос.

Список топиков и полный snapshot дерева пока без пагинации; поиск прикрепления постраничный. При возврате во вкладку/деталь и по «Обновить» выполняется чтение Room; отдельного catalogChanged event-stream пока нет. Навигация, выбранная ветка и несохранённые поля формы — состояние UI, не восстановление после смерти процесса. Сохранённое дерево/связи живут в Room. Нагрузочная приёмка больших каталогов остаётся отдельной задачей.
