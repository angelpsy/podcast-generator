## E-01 · HTTP 200 с SSE без Content-Type

**До исправления:** вход и список моделей работали, запрос ответа завершался `expected_event_stream`.

**Доказательства:** безопасная диагностика показала HTTP 200, отсутствие Content-Type и начало тела в формате SSE. Ответ не был обычным JSON. Добавление одного `Accept: text/event-stream` не устранило отсутствие заголовка.

**Причина:** клиент считал MIME-заголовок обязательным условием чтения потока, а наблюдавшийся ответ его не содержал. Причина отсутствия заголовка на стороне сервиса/сетевого пути не установлена.

**Изменение:** отправлять `Accept: text/event-stream`; при отсутствии/пустом Content-Type разрешать чтение только для начала `data:`, `event:` или SSE-комментария `:`. Явно заданный другой MIME, HTML и JSON не принимать. Завершение подтверждать только событием `response.completed`.

**Где:** `Protocol.isEventStream`, `SiwcCoordinator.sendPrompt`, безопасные поля диагностики в `state.ts`. Коммит: `18add99b5d7bb4aaf89a80202111bec6bc28131b`.

**Регрессия:** `ProtocolTest.acceptsMissingContentTypeOnlyForSseFraming`; чтение фрагментированных событий и отсутствие completion по `[DONE]`/EOF проверяются отдельными тестами. На Pixel получен ответ «Связь работает.», Completed в 00:18:41 Asia/Tbilisi.

## E-02 · DNS-ошибка после callback при повторной авторизации

**До исправления:** браузер завершал вход, но приложение останавливалось на Validating с общим `network_error`.

**Доказательства:** лог тега SiwcSpike связал сбой с `oauth_token`: `UnknownHostException`, причина `GaiException`; в этот момент Chrome был на переднем плане. Общая проверка DNS на телефоне проходила. Раннее объяснение об ошибке аккаунта или loopback-порта этим не подтверждалось.

**Установленная причина на уровне приложения:** обмен одноразового кода начинался сразу после callback в фоне. После переноса обмена на возврат приложения тот же сценарий заработал. Какая именно системная или сетевая политика вызвала DNS-сбой, отдельно не доказано; это не утверждение о запрете фоновой сети на всех Android-устройствах.

**Изменение:** LifecycleEventListener передаёт состояние foreground в `ForegroundGate`. После callback coordinator переходит в AwaitingReturn и ждёт максимум 120 секунд. Code находится только в памяти; обмен начинается после возврата, отмена/тайм-аут завершают попытку. Ожидание самого callback ограничено пятью минутами. DNS, TLS и настройки телефона не менялись; одноразовый code автоматически не повторяется.

**Где:** `ForegroundGate.kt`, `SiwcModule.kt`, `SiwcCoordinator.signIn`. Коммит: `f97b12e64920cf3b44fea5012a7e5169666367a1`.

**Регрессия:** три теста ForegroundGate проверяют ожидание, тайм-аут и отмену. На Pixel подтверждены повторный вход без выхода, revocation HTTP 200, SignedOut после холодного запуска, новый вход и успешный ответ новой сессии. Контрольные времена: Ready 00:28:46, выход 00:29:55, новый Ready 00:30:51, Completed 00:31:35 Asia/Tbilisi.

**Граница:** gate проверяет состояние перед обменом; он не гарантирует сеть при последующем сворачивании приложения или убийстве процесса. Такой сценарий отдельно не проверялся.

## E-03 · Недоступный SDK в первоначальном варианте RN

При подготовке среды SDK Manager не нашёл `platforms;android-37`, требовавшийся первоначально рассмотренному шаблону RN 0.87. Для эксперимента выбрана база RN 0.86.3 с compile/target SDK 36, NDK 27.1.12297006, CMake 3.22.1 и её Gradle Wrapper. Kotlin/AGP берутся из согласованной RN-конфигурации.

Проверка решения: Codegen, Kotlin/JNI, debug/release APK собраны; release APK запущен на телефоне с Android 17 / API 37. Версия ОС телефона не требует равного compile SDK проекта. Источник истории установки: [LOCAL_ENVIRONMENT.md](LOCAL_ENVIRONMENT.md), исходная реализация — `147aa61`. Это описание конкретной установки 24 октября, а не утверждение, что SDK 37 недоступен сейчас всем пользователям.

Предупреждения SDK XML/deprecated Gradle features не остановили проверенную сборку. Обновление инструментов ради устранения предупреждений не входит в исправление SIWC.

## N-01 · Почему браузер открывает 127.0.0.1

`http://127.0.0.1:<port>/auth/callback` ведёт в короткоживущий listener приложения на Pixel. Порт выбирается свободный при каждой попытке; один и тот же адрес используется в authorize и обмене кода. Это соответствует [официальному SIWC-потоку](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Страница `Sign-in received. Return to the app.` означает, что callback принят; проверка токенов ещё впереди. Нужно вернуться через Back или список приложений. SIWC не требует `adb reverse` или HTTP-сервера на Mac. `adb reverse tcp:8081 tcp:8081` относится только к Metro при разработке.

Если браузер показывает ошибку соединения, это уже другой случай: listener мог закрыться после отмены, тайм-аута, убийства процесса или при открытии старой вкладки. Начать новый вход из приложения. Не обновлять старый callback URL и не пересылать его целиком: он может содержать одноразовый code и state.

## R-01 · Полная обработка терминальных ошибок refresh

Исправлено после [ревью v0](CODE_REVIEW_V0_2026-10-25.md). `Protocol.terminalRefreshErrors` содержит единый набор: `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`. `httpErrorCode` сохраняет эти безопасные коды из строкового OAuth error и вложенного error.code. `RefreshFlow` очищает токены только при таких ошибках token endpoint; UI предлагает войти заново. Client ID, host ID и проверенная identity остаются для повторного входа. IOException, 5xx и `invalid_client` не очищают регистрацию или токены. Контракт: [OpenAI Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

Регрессия: `RefreshFlowTest.everyTerminalCodeSurvivesHttpParsingAndClearsOnlyTokens` проверяет все шесть кодов в двух форматах; `networkServerAndClientConfigurationErrorsPreserveCredentials` — сохранение сессии при временных сбоях и ошибке конфигурации. Это локальные JVM-тесты с подставными ответами, а не принудительный отзыв реальной сессии.

## R-02 · Сохранение ответа refresh до проверки JWKS

Добавлен небольшой `RefreshFlow.kt`, вызываемый тем же единственным executor coordinator. Новых библиотек, сервисов или экранов нет.

После получения и разбора ответа token endpoint сохраняются `pending_refresh.response` и время получения в существующем credential record. Этот record целиком шифруется прежним `CredentialStore` через Keystore/AtomicFile. Запись выполняется до следующей проверки отмены и до сетевого запроса JWKS. Pending-токены не становятся активными, не передаются в JS и не используются для inference.

При сбое JWKS или отмене следующий запрос сначала завершает проверку pending-ответа, даже если предыдущий access token ещё не истёк. Повторный refresh с предшествующим токеном не выполняется. При успешной проверке подписи и прежней identity весь набор заменяется, pending удаляется. Срок доступа вычисляется от первоначального времени получения, поэтому ожидание сети не продлевает жизнь токена. Сохранённая запись позволяет продолжить эту проверку после перезапуска процесса.

Выход пытается отозвать последний refresh-токен из pending-записи, затем удаляет и обычные токены, и pending. Новый успешный OAuth-вход также удаляет старую pending-запись. При неверной подписи или другой identity замена не активируется; можно явно выполнить новый вход или выход. Использование последней замены соответствует [OpenAI Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

Проверки в `RefreshFlowTest`:

- JWKS IOException → восстановление из сериализованной записи новым экземпляром flow → только один обмен с `r1`, активация `r2` после проверки;
- отмена сразу после получения ответа и после валидации → сохранение pending без преждевременной активации;
- сохранение исходного времени expiry и scopes при отсутствии новых scopes;
- реальная Nimbus-проверка тестовых JWT: неверная подпись и другая identity отклоняются;
- выход выбирает последний токен и удаляет pending; успешный новый вход заменяет pending.

**Границы:** автоматические тесты используют сериализованное подставное хранилище, не Android Keystore. Новую сборку на Pixel в этой задаче не устанавливали, реальное истечение/refresh ещё предстоит проверить. Внезапная потеря процесса или ответа до сохранения pending, а также ошибка диска с последующим перезапуском остаются случаями с неопределённым результатом ротации; может потребоваться новый OAuth-вход. Успешно сохранённый pending защищает именно от последующего сбоя JWKS/отмены. Внутри живого процесса pending удерживается и при ошибке записи, чтобы не отправлять предшествующий токен повторно.

Проверка исправлений 25 октября 2026 года: **18 JVM-тестов (8 новых), 1 Jest, TypeScript и ESLint — успешно; Android lint — 0 ошибок / 17 предупреждений; release APK собран**. Команда Android: `./gradlew --no-daemon --console=plain :app:testDebugUnitTest :app:lintDebug :app:assembleRelease`. Исходники: [RefreshFlow](../mobile/android/app/src/main/java/dev/podcast/siwcspike/siwc/RefreshFlow.kt), [тесты](../mobile/android/app/src/test/java/dev/podcast/siwcspike/siwc/RefreshFlowTest.kt).

## Короткий порядок диагностики

| Наблюдение | Действие |
| --- | --- |
| AwaitingReturn | Вернуться в приложение до тайм-аута; дождаться Ready |
| `authorization_timeout` / `app_return_timeout` | Запустить новую попытку через Continue with ChatGPT |
| `network_error` | Проверить интернет телефона и повторить действие в foreground; записать этап и класс исключения из безопасного лога |
| `expected_event_stream` | Проверить наличие исправления E-01; сохранить HTTP status, responseContentType и responseFormat |
| `stream_interrupted` | Частичный текст не считать завершённым; повторить запрос явно кнопкой |
| `revocation_unconfirmed` | Локальный выход завершён; удалённый отзыв проверить через настройки подключённых приложений ChatGPT |
| Ошибки refresh после простоя | Убедиться, что установлена сборка с исправлениями R-01/R-02; при временном сбое повторить действие, при терминальной ошибке войти заново в ту же регистрацию |

На одном подключённом по USB телефоне, из корня проекта:

```sh
source tools/android-env.sh
adb devices -l
adb -d logcat -d -s 'SiwcSpike:I' '*:S'
```

В приложении есть «Поделиться диагностикой»: экспорт исключает email, ответ и неизвестные поля. Для новой записи достаточно commit/build, даты и часового пояса, Android/browser, шага, ожидаемого и фактического результата, безопасного кода/HTTP/request ID и проверки после изменения. Не сохранять OAuth URL, токены, code/state/nonce, браузерные поля или полный logcat в Git. Не очищать данные приложения как обычный способ повторного входа: это удаляет сохранённую регистрацию и host ID.
