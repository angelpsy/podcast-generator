## E-01 · HTTP 200 с SSE без Content-Type

**До исправления:** вход и список моделей работали, запрос ответа завершался `expected_event_stream`.

**Доказательства:** безопасная диагностика показала HTTP 200, отсутствие Content-Type и начало тела в формате SSE. Ответ не был обычным JSON. Добавление одного `Accept: text/event-stream` не устранило отсутствие заголовка.

**Причина:** клиент считал MIME-заголовок обязательным условием чтения потока, а наблюдавшийся ответ его не содержал. Причина отсутствия заголовка на стороне сервиса/сетевого пути не установлена.

**Изменение:** отправлять `Accept: text/event-stream`; при отсутствии/пустом Content-Type разрешать чтение только для начала `data:`, `event:` или SSE-комментария `:`. Явно заданный другой MIME, HTML и JSON не принимать. Завершение подтверждать только событием `response.completed`.

**Где:** `Protocol.isEventStream`, `SiwcCoordinator.sendPrompt`, безопасные поля диагностики в `state.ts`. Коммит: `18add99b5d7bb4aaf89a80202111bec6bc28131b`.

**Регрессия:** `ProtocolTest.acceptsMissingContentTypeOnlyForSseFraming`; чтение фрагментированных событий и отсутствие completion по `[DONE]`/EOF проверяются отдельными тестами. На Pixel получен ответ «Связь работает.», Completed в 00:18:41 Asia/Tbilisi.

## E-02 · DNS-ошибка после callback при повторной авторизации

**До исправления:** браузер завершал вход, но приложение останавливалось на Validating с общим `network_error`.

**Доказательства:** лог тега SiwcSpike связал сбой с `oauth_token`: `UnknownHostException`, причина `GaiException`; в этот момент Chrome был на переднем плане. Общая проверка DNS на телефоне проходила. Раннее объяснение об ошибке аккаунта или loopback-порта этим не подтверждалось.

**Установленная причина на уровне приложения:** обмен одноразового кода начинался сразу после callback в фоне. После переноса обмена на возврат приложения тот же сценарий заработал. Какая именно системная или сетевая политика вызвала DNS-сбой, отдельно не доказано; это не утверждение о запрете фоновой сети на всех Android-устройствах.

**Изменение:** LifecycleEventListener передаёт состояние foreground в `ForegroundGate`. После callback coordinator переходит в AwaitingReturn и ждёт максимум 120 секунд. Code находится только в памяти; обмен начинается после возврата, отмена/тайм-аут завершают попытку. Ожидание самого callback ограничено пятью минутами. DNS, TLS и настройки телефона не менялись; одноразовый code автоматически не повторяется.

**Где:** `ForegroundGate.kt`, `SiwcModule.kt`, `SiwcCoordinator.signIn`. Коммит: `f97b12e64920cf3b44fea5012a7e5169666367a1`.

**Регрессия:** три теста ForegroundGate проверяют ожидание, тайм-аут и отмену. На Pixel подтверждены повторный вход без выхода, revocation HTTP 200, SignedOut после холодного запуска, новый вход и успешный ответ новой сессии. Контрольные времена: Ready 00:28:46, выход 00:29:55, новый Ready 00:30:51, Completed 00:31:35 Asia/Tbilisi.

**Граница:** gate проверяет состояние перед обменом; он не гарантирует сеть при последующем сворачивании приложения или убийстве процесса. Такой сценарий отдельно не проверялся.

## E-03 · Недоступный SDK в первоначальном варианте RN

При подготовке среды SDK Manager не нашёл `platforms;android-37`, требовавшийся первоначально рассмотренному шаблону RN 0.87. Для эксперимента выбрана база RN 0.86.3 с compile/target SDK 36, NDK 27.1.12297006, CMake 3.22.1 и её Gradle Wrapper. Kotlin/AGP берутся из согласованной RN-конфигурации.

Проверка решения: Codegen, Kotlin/JNI, debug/release APK собраны; release APK запущен на телефоне с Android 17 / API 37. Версия ОС телефона не требует равного compile SDK проекта. Источник истории установки: [LOCAL_ENVIRONMENT.md](LOCAL_ENVIRONMENT.md), исходная реализация — `147aa61`. Это описание конкретной установки 24 октября, а не утверждение, что SDK 37 недоступен сейчас всем пользователям.

Предупреждения SDK XML/deprecated Gradle features не остановили проверенную сборку. Обновление инструментов ради устранения предупреждений не входит в исправление SIWC.

## N-01 · Почему браузер открывает 127.0.0.1

`http://127.0.0.1:<port>/auth/callback` ведёт в короткоживущий listener приложения на Pixel. Порт выбирается свободный при каждой попытке; один и тот же адрес используется в authorize и обмене кода. Это соответствует [официальному SIWC-потоку](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

Страница `Sign-in received. Return to the app.` означает, что callback принят; проверка токенов ещё впереди. Нужно вернуться через Back или список приложений. SIWC не требует `adb reverse` или HTTP-сервера на Mac. `adb reverse tcp:8081 tcp:8081` относится только к Metro при разработке.

Если браузер показывает ошибку соединения, это уже другой случай: listener мог закрыться после отмены, тайм-аута, убийства процесса или при открытии старой вкладки. Начать новый вход из приложения. Не обновлять старый callback URL и не пересылать его целиком: он может содержать одноразовый code и state.

## R-01 · Полная обработка терминальных ошибок refresh

Исправлено после [ревью v0](CODE_REVIEW_V0_2026-10-25.md). `Protocol.terminalRefreshErrors` содержит единый набор: `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`. `httpErrorCode` сохраняет эти безопасные коды из строкового OAuth error и вложенного error.code. `RefreshFlow` очищает токены только при таких ошибках token endpoint; UI предлагает войти заново. Client ID, host ID и проверенная identity остаются для повторного входа. IOException, 5xx и `invalid_client` не очищают регистрацию или токены. Контракт: [OpenAI Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).

Регрессия: `RefreshFlowTest.everyTerminalCodeSurvivesHttpParsingAndClearsOnlyTokens` проверяет все шесть кодов в двух форматах; `networkServerAndClientConfigurationErrorsPreserveCredentials` — сохранение сессии при временных сбоях и ошибке конфигурации. Это локальные JVM-тесты с подставными ответами, а не принудительный отзыв реальной сессии.

## R-02 · Сохранение ответа refresh до проверки JWKS

Добавлен небольшой `RefreshFlow.kt`, вызываемый тем же единственным executor coordinator. Новых библиотек, сервисов или экранов нет.

После получения и разбора ответа token endpoint сохраняются `pending_refresh.response` и время получения в существующем credential record. Этот record целиком шифруется прежним `CredentialStore` через Keystore/AtomicFile. Запись выполняется до следующей проверки отмены и до сетевого запроса JWKS. Pending-токены не становятся активными, не передаются в JS и не используются для inference.

При сбое JWKS или отмене следующий запрос сначала завершает проверку pending-ответа, даже если предыдущий access token ещё не истёк. Повторный refresh с предшествующим токеном не выполняется. При успешной проверке подписи и прежней identity весь набор заменяется, pending удаляется. Срок доступа вычисляется от первоначального времени получения, поэтому ожидание сети не продлевает жизнь токена. Сохранённая запись позволяет продолжить эту проверку после перезапуска процесса.

Выход пытается отозвать последний refresh-токен из pending-записи, затем удаляет и обычные токены, и pending. Новый успешный OAuth-вход также удаляет старую pending-запись. При неверной подписи или другой identity замена не активируется; можно явно выполнить новый вход или выход. Использование последней замены соответствует [OpenAI Accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

Проверки в `RefreshFlowTest`:

- JWKS IOException → восстановление из сериализованной записи новым экземпляром flow → только один обмен с `r1`, активация `r2` после проверки;
- отмена сразу после получения ответа и после валидации → сохранение pending без преждевременной активации;
- сохранение исходного времени expiry и scopes при отсутствии новых scopes;
- реальная Nimbus-проверка тестовых JWT: неверная подпись и другая identity отклоняются;
- выход выбирает последний токен и удаляет pending; успешный новый вход заменяет pending.

**Границы:** автоматические тесты используют сериализованное подставное хранилище, не Android Keystore. После unit-проверок сборка `2168399` установлена на Pixel: настоящий явный refresh, холодный запуск, ответ, выход и повторный вход прошли. Естественное истечение и аварийные сценарии на устройстве ещё не проверены; подробности ниже. Внезапная потеря процесса или ответа до сохранения pending, а также ошибка диска с последующим перезапуском остаются случаями с неопределённым результатом ротации; может потребоваться новый OAuth-вход. Успешно сохранённый pending защищает именно от последующего сбоя JWKS/отмены. Внутри живого процесса pending удерживается и при ошибке записи, чтобы не отправлять предшествующий токен повторно.

Проверка исправлений 25 октября 2026 года: **18 JVM-тестов (8 новых), 1 Jest, TypeScript и ESLint — успешно; Android lint — 0 ошибок / 17 предупреждений; release APK собран**. Команда Android: `./gradlew --no-daemon --console=plain :app:testDebugUnitTest :app:lintDebug :app:assembleRelease`. Исходники: [RefreshFlow](../mobile/android/app/src/main/java/dev/podcast/siwcspike/siwc/RefreshFlow.kt), [тесты](../mobile/android/app/src/test/java/dev/podcast/siwcspike/siwc/RefreshFlowTest.kt).

## TTS-01 · Native crash при вызове Kotlin callback из sherpa-onnx

25 октября 2026, 01:52:57 UTC+4, Pixel 10 Pro / Android 17. Первый тест Supertonic в APK `005ed91d…` загрузил модель за примерно 2.8 секунды и начал первый фрагмент, затем процесс завершился с SIGABRT. M4A ещё не был создан; SIWC-хранилище не затрагивалось.

Причина из native crash: `NoSuchMethodError` для `invoke([F)Ljava/lang/Integer;` у `LocalTtsEngine$$ExternalSyntheticLambda0`. sherpa-onnx JNI ищет конкретный typed method на объекте callback. Kotlin 2.x / D8 сгенерировал для переданной лямбды класс без этой сигнатуры; JNI продолжил работу с pending exception и ART завершил процесс. Обычный Kotlin try/catch вокруг generate не защищает от такого native abort.

Исправление: именованный `@Keep SherpaAudioCallback : (FloatArray) -> Int` с явным `invoke`. Callback возвращает 0 при отмене/тайм-ауте, исключения не передаются через JNI. Binding и бинарные библиотеки upstream не изменялись. Добавлены JVM-проверка точной сигнатуры метода через reflection и проверка возврата stop при отмене. Повторный результат на Pixel фиксируется в отчёте локальной озвучки.

## TTS-02 · Корректный AAC отклонён из-за отрицательного PTS первого пакета

Первый полный синтез русского образца завершился 25 октября в 01:55:12 UTC+4, но проверка M4A возвращала `missing_audio_samples`. Приложение сохранило WAV, поэтому повтор выполнялся с этапа Encoding, в том числе после перезапуска и установки диагностической сборки.

Проверка формата показала одну дорожку AAC-LC, mono, 44100 Hz, длительность 46.1 секунды. Ошибочной была проверка `extractor.sampleTime >= 0`: первый AAC-пакет имел PTS −36281 микросекунд и размер 278 байт. Отрицательное время priming не означает отсутствие аудиоданных.

Исправление: после выбора дорожки прочитать первый пакет через `readSampleData` и проверить ненулевой размер. Проверки контейнера, AAC profile, каналов и длительности сохраняются. После исправления M4A успешно опубликован через MediaStore в 01:58:34; AIMP получил URI и начал воспроизведение. Пользователь подтвердил, что русская речь слышна и понятна.

Независимая проверка на Mac: `afinfo` — AAC mono 44100 Hz, 96004 bit/s, 46.090 секунд; `afconvert` декодировал файл полностью в PCM. WAV и текст заново не генерировались при повторе кодирования. Это реальная проверка восстановления этапа после ошибки, а не только JVM mock.

## P-01 · Завершающее SSE-событие не повторяет уже полученный текст

25 октября 2026 года, 02:20:02 Asia/Tbilisi: первый запрос полного подкаста получил HTTP 200 и корректный SSE, но новый общий collector вернул `empty_script`. Озвучка не запускалась, старый M4A остался. Причина: collector заменял накопленные `response.output_text.delta` на содержимое `response.completed.response.output`, даже когда в терминальном событии не было текстовых частей.

Исправление: при наличии текстовых частей в completed использовать их без дублирования; если частей нет, сохранить накопленные deltas. Успех по-прежнему требует `response.completed`, непустого результата и лимита длины. EOF, incomplete, refusal и ошибки не запускают TTS. Тест `siwcCompletionMayOmitTextAlreadyStreamedAsDeltas` покрывает как успешные deltas + пустой output, так и действительно пустой ответ.

Повтор на Pixel в 02:21:54 подтвердил формат: `streamed_chars=1010`, `final_text_parts=0`, затем `Completed` и `Synthesizing`. Диагностика содержит только длину и количество частей, без темы/текста. Сценарий проверяется через текущую SIWC-сессию; отдельный API key или новый вход не потребовались. Полный результат и артефакт: [отчёт подкаста](DEVICE_PODCAST_TEST_2026-10-25.md).

## P-02 · Сбой MediaStore принимался за отсутствие записи

Обнаружено при [ревью 1.2](CODE_REVIEW_PODCAST_V1_2_2026-10-25.md), 25 октября 2026 года. `ContentResolver.query()` может вернуть null при ошибке провайдера. Адаптер считал это отсутствием файла или успешным завершением удаления. В JVM-проверке восстановление удаляло уже опубликованный M4A; при другом null-запросе очистка забывала URI старой записи, оставляя лишний файл. Сбой системного провайдера на Pixel не вызывался.

Исправление: небольшой `AudioMediaRows` используется во всех трёх запросах (`find`, `isPublished`, `delete`). Null теперь вызывает `IOException("media_query_failed")`. Только успешный пустой Cursor подтверждает отсутствие строки. Поэтому при недоступном запросе journal сохраняет pending/cleanup, новый опубликованный файл не удаляется, а следующая попытка завершает восстановление. Проверка владельца перед удалением остаётся обязательной.

Регрессии: 4 теста чтения Cursor проверяют null, пустой результат, флаг публикации, владение и ошибку удаления. Ещё 3 сценария `LatestAudioStoreTest` проходят через тот же reader: сбой проверки опубликованного файла после crash до commit; сбой проверки владельца с повтором очистки и блокировкой третьего выпуска; сбой поиска после insert до записи URI. После восстановления запросов остаётся ровно нужный файл без дубликатов.

Исходники: [AudioMediaRows](../mobile/android/app/src/main/java/dev/podcast/siwcspike/podcast/AudioMediaRows.kt), [тесты reader](../mobile/android/app/src/test/java/dev/podcast/siwcspike/podcast/AudioMediaRowsTest.kt), [тесты восстановления](../mobile/android/app/src/test/java/dev/podcast/siwcspike/podcast/LatestAudioStoreTest.kt).

## P-03 · Плеер не повторял воспроизведение того же URI после ошибки

Обнаружено при ревью 1.2. После `onPlayerError` Media3 переводит плеер в `STATE_IDLE`. Прежняя команда «Слушать» вызывала `prepare()` только при изменении URI; `play()` на том же файле не выводил плеер из idle.

Исправление: `playPodcast` вызывает `prepare()` при новом media item **или** `STATE_IDLE`, затем запускает воспроизведение. Обычное продолжение из паузы сохраняет позицию, а завершённый файл запускается с начала. 4 JVM-теста используют подставной `Player` по контракту Media3: повтор после ошибки на том же URI, обычная пауза, конец файла и новый media item. Реальная ошибка декодера на телефоне не провоцировалась.

## P-04 · Кнопка продолжения появлялась без сохранённого черновика

## V2-L01 · Глобальная замена файла и черновика несовместима с библиотекой

**Основание:** прежнее намеренное ограничение 1.2, а не новая потеря данных на устройстве. Глобальный `current.json` удалял предыдущий M4A после публикации, а новое создание очищало единственный draft. При переходе к библиотеке такой протокол терял бы соседние выпуски и незавершённые задания.

## V2-L02 · Неизвестное состояние миграции нельзя принимать за пустую библиотеку

Ошибка удаления оставляет DELETING. В обработчике ошибки генерации путь временных файлов захвачен заранее: очистка не делает дополнительный запрос к уже отказавшей Room.

**Проверка:** fixtures повреждённого JSON/неверной формы, откат импорта при конфликте и успешный повтор, null provider после insert, published-before-commit, FILE_MISSING и повтор удаления. ## V2-T01 · Каскад удаления ссылки должен менять revision топика

## V2-T02 · Перенос должен проверять всю ветку и сохранять активную очередь

**Защитные сценарии нового дерева:** узел может помещаться на четвёртом уровне, а его потомок — уже на запрещённом пятом. Параллельное редактирование также нельзя применять без проверки версии. Реальной потери дерева/аудио при разработке не наблюдалось.

**Решение:** единые TopicTree rules для команды и выбора родителя: root=0, глубина всей ветки ≤4, запрет циклов/self/cross-topic и детей QUESTION. Reorder и нормализация позиций транзакционны. expectedRevision отклоняет старое изменение; ошибка не применяет часть дерева. Плейлист вычисляется DFS с MAIN-first и dedupe, а Player получает независимый снимок IDs.

**Проверка:** 15 JVM и 14 новых Android-сценариев; rejected move не меняет snapshot. Производственный MediaController продолжил ту же очередь после переноса, отвязки, удаления топика и Activity.recreate. Удаление целого топика, ветки и связи также проверено обычным UI. ## V2-O02 · Позднее предложение не должно применять старый контекст

**Защищённый сценарий:** после запроса топик/ветка могут измениться. Нельзя автоматически присвоить предложению новую базовую revision и считать его актуальным. Replace также может снять связи с уже изменившихся потомков.

**Решение:** неизменяемые input/baseRevision, отдельная reviewedRevision, актуальный diff с названиями путей и числом связей. При конфликте Apply отключён; пользователь явно подтверждает новый просмотр, затем отдельно применение. Транзакция повторяет проверку revision, глубины, ёмкости и дублей. QUESTION преобразуется в SECTION только при Apply; ID, собственные связи и аудио сохраняются.

**Проверка:** изолированные Room-сценарии конфликта и повторной правки между review/Apply, перемещения ветки, замены и сохранения audio journals прошли. В обычном UI после холодного запуска показаны исходный научный и новый технический контекст; Apply был disabled. Повторный просмотр обновил reviewedRevision 0 → 2, исходная baseRevision осталась 0. Научный план отклонён, корректная техническая ветка применена отдельно. Home отменил новый запрос замены без изменения восьми узлов.

## V2-G02 · Редактор очереди не должен ждать окончания TTS

Первоначально preview/enqueue были поставлены на тот же executor, что и длительная озвучка. Это задерживало ответ формы до завершения текущего выпуска. ## Диагностика SIWC

| Наблюдение | Действие |
| --- | --- |
| AwaitingReturn | Вернуться в приложение до тайм-аута; дождаться Ready |
| `authorization_timeout` / `app_return_timeout` | Запустить новую попытку через Continue with ChatGPT |
| `network_error` | Проверить интернет телефона и повторить действие в foreground; записать этап и класс исключения из безопасного лога |
| `expected_event_stream` | Проверить наличие исправления E-01; сохранить HTTP status, responseContentType и responseFormat |
| `stream_interrupted` | Частичный текст не считать завершённым; повторить запрос явно кнопкой |
| `revocation_unconfirmed` | Локальный выход завершён; удалённый отзыв проверить через настройки подключённых приложений ChatGPT |
| Ошибки refresh после простоя | Убедиться, что установлена сборка с исправлениями R-01/R-02; при временном сбое повторить действие, при терминальной ошибке войти заново в ту же регистрацию |

На одном подключённом по USB телефоне, из корня проекта:

```sh
source tools/android-env.sh
adb devices -l
adb -d logcat -d -s 'SiwcSpike:I' '*:S'
```

В приложении есть «Поделиться диагностикой»: экспорт исключает email, ответ и неизвестные поля. Для новой записи достаточно commit/build, даты и часового пояса, Android/browser, шага, ожидаемого и фактического результата, безопасного кода/HTTP/request ID и проверки после изменения. Не сохранять OAuth URL, токены, code/state/nonce, браузерные поля или полный logcat в Git. Не очищать данные приложения как обычный способ повторного входа: это удаляет сохранённую регистрацию и host ID.

Ревью приложения выявило два открытых замечания P2:

1. **StorageError обрабатывается непоследовательно.** Hook проверяет его только при отсутствии массива generationQueue: при неудачном recover после ранее загруженной очереди ошибка скрыта, Resume остаётся доступным при storageReady=false. 2. **Повтор загрузки не восстанавливает хранилище.** Retry лишь повторяет getSnapshot, который отдаёт сохранённый state. После настоящего StorageError возвращается та же ошибка; путь recoverLibrary не вызывается. Следует различать ошибку доставки snapshot и ошибку загрузки библиотеки, для второй использовать существующее восстановление и дождаться его результата.

Оба замечания подтверждены тремя изолированными воспроизведениями: скрытый новый StorageError с кэшированными заданиями, ложная ошибка от старого ответа и повтор чтения неизменного StorageError без recovery.
