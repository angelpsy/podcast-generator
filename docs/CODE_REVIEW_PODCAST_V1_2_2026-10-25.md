## 1. P2 — null от MediaStore нельзя считать отсутствием файла

Файл: [AndroidAudioStorage.kt](../mobile/android/app/src/main/java/dev/podcast/siwcspike/podcast/AndroidAudioStorage.kt), `isPublished` (строки 74–77), `delete` (87–90), аналогично `find` (43–46).

`ContentResolver.query()` может вернуть null при сбое провайдера; отсутствие подходящей записи обозначается пустым Cursor. Сейчас адаптер превращает null в `false`, отсутствие URI или успешный выход из `delete`. [Контракт Android](https://developer.android.com/reference/android/content/ContentResolver#query(android.net.Uri,%20java.lang.String[],%20android.os.Bundle,%20android.os.CancellationSignal)).

Последствия для `LatestAudioStore`:

- После сбоя между публикацией и commit journal восстановление вызывает `isPublished`. Null превращается в false; если следующий запрос владельца уже успешен, `recover()` удаляет полностью опубликованный новый M4A как незавершённый.
- При null в проверке владельца `delete()` возвращает успех без удаления. `cleanup()` убирает сохранённый URI очистки, старый M4A остаётся в папке и больше не удаляется при следующих выпусках. Нарушается правило «только последний файл».

Проверка: временный JVM probe запускал **скомпилированный класс приложения `LatestAudioStore`**, подставляя результаты, соответствующие null-веткам Android-адаптера. В первом сценарии после recovery остался старый current, новый опубликованный файл удалён. Во втором после создания третьего выпуска остались `old` и `third`, при этом `cleanupPending=false`. Реальный сбой системного провайдера на Pixel не вызывался.

Минимальное исправление: null Cursor считать ошибкой чтения и сохранять journal для следующей попытки. Только успешно прочитанный пустой Cursor означает отсутствие записи. Дополнить тесты восстановления и очистки случаем недоступного запроса.

## 2. P2 — «Слушать» не восстанавливает ExoPlayer после ошибки

Файл: [PodcastCoordinator.kt](../mobile/android/app/src/main/java/dev/podcast/siwcspike/podcast/PodcastCoordinator.kt), `play()` (строки 309–313).

После `onPlayerError` ExoPlayer переходит в `STATE_IDLE`; повтор требует `prepare()`. [Поведение Media3](https://developer.android.com/media/media3/exoplayer/listening-to-player-events#playback_errors).

Здесь `prepare()` вызывается только при изменении URI. После временной ошибки чтения/декодирования `playerUri` сохраняется. Следующее нажатие «Слушать» на том же файле вызывает только `play()`, поэтому плеер остаётся idle и не повторяет загрузку. Перезапуск приложения или создание нового выпуска обходят проблему, но обычная кнопка повтора не работает.

Минимальное исправление: при том же URI и `STATE_IDLE` повторно подготовить плеер. Проверить цепочку error → исправная доступность файла → «Слушать» без смены URI. Вывод получен из кода и контракта Media3; аппаратная ошибка декодера на Pixel не провоцировалась.

## 3. P2 — доступность продолжения определяется объектом в памяти

Файл: [PodcastCoordinator.kt](../mobile/android/app/src/main/java/dev/podcast/siwcspike/podcast/PodcastCoordinator.kt), обработчик ошибки, строка 253; создание черновика — строки 143–149.

`meta` получает ненулевой JSONObject **до** записи `input.json` и `draft/meta.json`. Если запись падает, например из-за нехватки места, обработчик всё равно выставляет `canRetry=true`. После освобождения места «Продолжить с сохранённого этапа» читает отсутствующий `meta.json` как пустой JSONObject, получает `no_draft` и снова выставляет `canRetry=true`, потому что пустой объект тоже ненулевой. Получается повторяющаяся ошибка; для продолжения пользователю приходится заново нажать «Создать подкаст».

Минимальное исправление: вычислять возможность продолжения по реально сохранённому валидному черновику либо явно поддержать повтор его первоначальной записи. Добавить сценарий отказа первой записи metadata и последующего повтора после восстановления хранилища. Это анализ ветвей кода; реальное заполнение диска Pixel не выполнялось.

## Проверки и ограничения

- JVM-набор: 43 теста, без ошибок. TypeScript, ESLint и Jest (1 тест) пройдены.
- Текущие storage-тесты проверяют выброшенные исключения, но не null-ответ Android ContentResolver; тесты черновика проверяют готовый script, но не ошибку его первоначального создания в coordinator.
- У плеера нет теста восстановления после `onPlayerError`.
- Полный сценарий и субъективная проверка речи уже подтверждены в [отчёте Pixel](DEVICE_PODCAST_TEST_2026-10-25.md). В рамках ревью новые запросы OpenAI не отправлялись, сборка на телефоне не менялась.

Первоначальная рекомендация выполнена: исправлены MediaStore recovery/cleanup и два повтора — воспроизведения и создания черновика. Архитектура и зависимости прототипа сохранены.
