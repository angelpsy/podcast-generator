## Структурированный ответ через SIWC — подтверждён

Использована доступная в каталоге текущего аккаунта модель `gpt-6.1-sol`. Новый OAuth-вход и API key не потребовались. В общий request builder добавлен необязательный `text.format`; по умолчанию прежние запросы не меняются. Регрессионный тест проверяет точное вложение format и независимость от последующего изменения объекта schema вызывающим кодом.

Первый запрос: тема «Клиент-серверное взаимодействие», JSON Schema с `strict:true`, обязательными полями и `additionalProperties:false`. Ответ — название топика, два раздела и по два вопроса. Получен terminal completion, выполнена локальная проверка всех полей и размеров массивов. Полный проход с загрузкой каталога — **11 708 мс**. Сценарий подкаста и аудио не создавались.

Вторая, контрольная проверка: prompt просит ответить обычным текстом `hello`, а schema требует единственное поле `schema_result` с единственным допустимым значением `format_enforced`. Возвращён именно объект по схеме, без дополнительных полей. Это отличает результат от простого JSON, который модель могла бы написать только по текстовой инструкции.

Обе проверки: PASS. Fallback на свободный JSON не понадобился. Результат подтверждает проверенную схему и модель в этой SIWC-регистрации; не доказывает поддержку всех конструкций JSON Schema или других моделей. [OpenAI Docs: Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses).

### Отмена

В отдельном локальном прогоне запрос отмены поставлен через 1,5 с после начала синтеза английского фрагмента. Native-вызов вернулся ещё через **10 071 мс**; полный прогон — 11 573 мс. Финальный `cancel.wav` не появился, остался только временный 44-байтный заголовок, удалённый тестом. Responses не вызывался. Проверка PASS, пользовательский journal неизменён.

Вывод для v2: «Пауза/Отмена» должна показывать промежуточное состояние, не запускать второй TTS до возврата первого и не принимать поздний результат за готовый. Нельзя обещать мгновенную отмену по одному флагу. Отмена на других фрагментах/языках и во время кодирования требует своих проверок.

Сценарии предметно различаются: технический объясняет лексическое окружение, привязки, var/let, this и память; научпоп разворачивает историю спектроскопии, наблюдения и ограничения выводов. Научпоп не получил обязательный список «типичных ошибок». Просмотр организации текста не заменяет независимую проверку всех научных/исторических утверждений; web-research внутри запроса не использовался.

## Проверка фонового плеера

Использован отдельный StageZeroPlaybackService с ExoPlayer + MediaSession. Он играет `english.m4a` и копию прежнего подкаста `baseline.m4a` последовательно с repeat-all. Цель — проверить жизненный цикл и смену треков; продуктовая очередь v2 пока не реализована. [Android: MediaSessionService](https://developer.android.com/media/media3/session/background-playback).

Первый запуск выявил ошибку: при shell-start не было MediaController binding, поэтому одного создания MediaSession оказалось недостаточно — сессия не была добавлена в сервис. Воспроизведение началось, но foreground-уведомление не появилось; примерно через 30 секунд Android завершил процесс с `ForegroundServiceDidNotStartInTimeException`. Артефакты сохранены в `playback-first-start.json` и `playback-first-start-crash.log`.

Исправление эксперимента: после построения сессии вызвать `addSession(session)`. Повторный запуск подтвердил `isForeground=true`, тип `0x2` (mediaPlayback), уведомление MediaStyle с тремя действиями, активную медиасессию приложения. В 14:02:17 выполнены Home и Sleep, WindowManager подтвердил заблокированный экран. Сервис каждые 5 секунд сохраняет положение, текущий трек, число переходов, player errors и `isInteractive`.

Итог короткой проверки: до 14:06:54 экран оставался заблокированным — около **4 минут 37 секунд**, с намеренной паузой для проверки управления. В последнем играющем snapshot — `isPlaying=true`, `interactive=false`, 53 наблюдения с выключенным экраном, 0 player errors, 5 стартов/переходов трека за весь запуск (2 до блокировки, 3 после). Foreground-сервис продолжал работу. Проверка в середине: системная медиаклавиша ADB Pause дала `isPlaying=false`, позиция 36 405 мс; Play без разблокировки возобновила движение позиции до 88 948 мс, затем очередь перешла дальше. В конце снова выполнена Pause, затем сервис остановлен.

Это подтверждает короткий foreground-playback smoke test с экраном блокировки и системными медиакомандами. Реальная Bluetooth-гарнитура, нажатия UI-кнопок lock screen, 15-минутный/многочасовой прогон, автономная работа без зарядки и deep Doze пока не проверены. Телефон был подключён по USB и питался от Mac; PowerManager показывал Dozing. Сэмплирование состояния раз в 5 секунд не исключает коротких слышимых дефектов между точками.

## Воспроизведение проверок

Из корня `mobile/android`, после `source ../../tools/android-env.sh`:

```sh
./gradlew :app:assembleStageZero :app:assembleStageZeroAndroidTest -PstageZeroChecks=true
adb install -r app/build/outputs/apk/stageZero/app-stageZero.apk
adb install -r app/build/outputs/apk/androidTest/stageZero/app-stageZero-androidTest.apk
adb shell am instrument -w -e mode outline dev.podcast.siwcspike.test/dev.podcast.siwcspike.podcast.StageZeroChecks
```

Другие mode: `schema-control`, `english`, `texts`, `long-tech`, `long-science`, `cancel`. `long-*` используют сохранённые файлы из `texts`, без нового OpenAI-запроса. `outline-fallback` существует для явно выбранной проверки свободного JSON, но здесь не запускался. Проверять `result:PASS` и `INSTRUMENTATION_CODE:-1`, а не только exit code ADB.

Запуск сервиса после окончания instrumentation (он перезапускает процесс):

```sh
adb shell am start -W -n dev.podcast.siwcspike/.MainActivity
adb shell am start-foreground-service -n dev.podcast.siwcspike/.podcast.StageZeroPlaybackService --es command play --es files english.m4a,baseline.m4a --ez repeat true
```

Первый сервисный прогон запущен shell-командой при открытом приложении. Это не доказывает право произвольного запуска сервиса из фона: shell имеет системные исключения. Поэтому выполнена отдельная проверка обычного app-owned MediaController, описанная ниже. Восстановление после Force stop/reboot и полный UI остаются последующими этапами.

### Дополнительный запуск через MediaController приложения

В последней экспериментальной сборке добавлена StageZeroPlaybackActivity, существующая только в stageZero. Она создаёт MediaController и подключается к SessionToken сервиса, ставит очередь длинных M4A, запускает play, затем через 5 секунд завершает Activity и освобождает controller.

Проверка: спустя 15 с Activity уже отсутствовала на экране (показан launcher), а сервис играл `long-science.m4a`. ActivityManager подтвердил запуск **из пакета приложения**, состояние вызывающего `TOP`, основание `PROC_STATE_TOP`, `isForeground=true`, mediaPlayback и уведомление. Это обычный путь приложения, не привилегированный shell-startForegroundService. На 100-й секунде запись всё ещё воспроизводилась без player errors, после уничтожения контроллера.

Затем экран заблокирован, выполнен seek к последним 15 секундам научпопа. Очередь сама перешла на `long-tech.m4a`; на отметке 195 938 мс с начала сервисного прогона он играл уже 75 452 мс следующего трека. В snapshot: `interactive=false`, 20 наблюдений с выключенным экраном, 2 старта/перехода, 0 errors. Foreground-сервис и keyguard подтверждены отдельно. Не проверялись следующий полный трек до конца, физическая гарнитура и пользовательский экран управления будущей v2.

Воспроизвести запуск при разблокированном устройстве:

```sh
adb shell am start -W -n dev.podcast.siwcspike/.podcast.StageZeroPlaybackActivity --es files long-science.m4a,long-tech.m4a
```
