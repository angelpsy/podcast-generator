# Этап 4: предложения структуры через SIWC

Дата: 25 октября 2026, Asia/Tbilisi. Android **1.6 / versionCode 7**, Pixel 10 Pro / Android 17. Обновление через `adb install -r`, без очистки данных и смены подписи. Ни API key, ни отдельный платный маршрут не добавлены.

## Реализация

В существующем топике или ветке доступно «Предложить структуру». Выбираются модель из каталога текущей SIWC-сессии, добавление либо замена дочерних узлов, глубина и лимит новых узлов; можно задать пожелание к плану. Структура пока русская; языковые профили и создание подкастов из узлов относятся к этапу 5.

Запрос использует Responses/SSE, `store:false`, `text.format` со строгой рекурсивной JSON Schema `podcast_outline_v1`. Выбранная модель не подменяется, если исчезла из каталога. Этот способ соответствует [официальному формату Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses); локальная валидация остаётся обязательной. Автоматического повторного запроса, переключения модели или текстового fallback в 1.6 нет.

Приложение принимает только обязательные поля `title`, `description`, `children`, а для узлов ещё `kind: SECTION | QUESTION`. Проверяет строгий JSON, повторяющиеся ключи, дополнительные поля, заголовки/описания, одинаковые названия соседей, конечность вопросов, глубину и число узлов. Ответ ограничен 32 768 code points и 128 KiB UTF-8; JSON-вложенность проверяется до обхода дерева. Максимум 50 новых узлов и 200 в топике вместе с корнем; максимум четыре уровня ниже корня, доступная глубина уменьшается при раскрытии вложенной ветки.

Полученный результат сохраняется как READY-предложение. До явного применения не меняются узлы, связи, библиотека или файлы. Предпросмотр показывает исходный и актуальный контекст, добавляемые и удаляемые узлы, число снимаемых связей. Верхнее название плана не переименовывает выбранный узел. Можно отклонить предложение. После применения дерево редактируется прежними ручными действиями; отдельный редактор JSON не добавлен.

Добавление сохраняет прежних детей и ставит новых в конец. Замена удаляет только потомков выбранного узла и их связи. Сам выбранный узел, его прикреплённые выпуски и все аудиофайлы сохраняются. Раскрытие конечного вопроса преобразует его в раздел только при применении, сохраняя ID и связи. Загруженная очередь плеера не меняется.

## Хранение и конкуренция

Room **4**, явная миграция **3 → 4**, цепочка **1 → 2 → 3 → 4**, без destructive fallback. Новая таблица `outline_proposals` хранит ID, topic/node, исходную и просмотренную revisions, режим, лимиты, модель, неизменяемый вход с promptVersion, статус, проверенный JSON, безопасный код ошибки и дату. FK удаляет предложения вместе с их веткой; поздний ответ не воссоздаёт удалённые записи. SIWC остаётся в прежнем защищённом хранилище.

Исходная `baseRevision` неизменяема. `reviewedRevision` изначально равна ей. Если дерево изменилось, Apply заблокирован: пользователь сначала просматривает актуальные добавления/удаления и явно подтверждает этот просмотр. Это обновляет только `reviewedRevision`, сохраняя исходный запрос. Отдельное подтверждение Apply снова сравнивает актуальную revision и выполняет всю замену/добавление одной транзакцией. Новая правка между просмотром и Apply снова вызывает конфликт. Повтор уже применённого ID не создаёт дубликаты.

Один OutlineCoordinator резервирует запрос до постановки в worker; двойное нажатие не создаёт два задания. Сетевой запрос не держит транзакцию и не блокирует ручное редактирование дерева. READY переживает холодный запуск. Оставшийся после смерти процесса RUNNING становится INTERRUPTED, без автоматического запроса. Уход приложения в фон/блокировка отменяет запрос структуры; фоновый плеер независим. Последние десять предложений выбранной ветки отображаются в UI; старые записи пока не очищаются автоматически.

## Проверки

- JVM: строгий парсер, неверные поля/типы/JSON, дубли, Unicode, лимиты текста/размера/вложенности, глубины 1–4, граница 50 узлов; прежние проверки SIWC и подкастов.
- Изолированная Room на Pixel: миграция 3 → 4 сохраняет топики/связи, готовый выпуск, черновик, playback и legacy-маркер; запрос/preview ничего не создаёт; append/idempotency; replace с сохранением аудио и собственных связей; QUESTION → SECTION; конфликт и повторный конфликт после просмотра; failure/cancel/interruption/discard; удаление ветки и поздний ответ; дубли, глубина и ёмкость; READY после закрытия/открытия базы.
- Реальные запросы `gpt-6.1-sol` через прежнюю SIWC-сессию: научная тема «Звёзды» и конкретный вопрос «Как работают HTTP и API?» в техническом топике. Оба ответа прошли строгую схему и локальную проверку. В каждом ответе шесть новых узлов. До применения новых Podcast/AudioAsset не появилось, исходные audio journals совпали. Во время активного запроса второй start отклонён как outline_busy.

Проверки отказа, неполного SSE и обрыва опираются на прежние тесты ResponseText и безопасное отклонение неполного результата; серверные отказ/429 не провоцировались специально. Полные 15 минут фонового playback повторно не выполняются: сервис не изменён, длительный тест сохранён в протоколе этапа 2. Численные лимиты — проектные ограничения, а не ограничения подписки или сервера.

## Повтор

Из корня репозитория:

```sh
source tools/android-env.sh
cd mobile/android
./gradlew :app:testReleaseUnitTest :app:assembleRelease :app:assembleReleaseAndroidTest -PoutlineChecks=true
adb install -r app/build/outputs/apk/release/app-release.apk
adb install -r app/build/outputs/apk/androidTest/release/app-release-androidTest.apk
adb shell am instrument -w dev.podcast.siwcspike.test/dev.podcast.siwcspike.podcast.OutlineDeviceChecks
```

Без аргумента live используются только изолированные базы, которые удаляются в finally. Добавление `-e live true` перед component запускает ещё два настоящих запроса с лимитами текущей подписки и оставляет пример топика/предложения для проверки UI. Телефон должен быть разблокирован, приложение — в foreground, с подключённой SIWC-сессией. Тест ждёт стартовую загрузку каталога; одновременные instrumentation и ручные сетевые действия не требуются. Не очищать данные приложения.

## Выявленные ошибки проверки

Первый запуск фикстуры остановился из-за отсутствующего `indices` у таблиц без индексов в экспорте Room. Затем уточнены обязательный outlineDepth и URI фиктивного AudioAsset: проверки attachment правильно отклоняли неполную запись. Исправления касались тестовых данных; production-валидация не ослаблялась.

Первый реальный запуск получил `operation_busy`: тест стартовал одновременно с автоматическим запросом каталога на React mount. В тест добавлено ожидание завершения стартовой загрузки и callback каталога. Повтор прошёл; приложение сохраняет такой отказ как FAILED и не повторяет запрос скрыто.
